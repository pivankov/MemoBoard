# Документация MemoBoard

Цель: документация — компактный справочник без воды. Не учебник для новичка. Один факт — в одном месте.

## Где правило не действует

Правило не применяется к следующим файлам, у каждого свой стандарт:

- `.cursor/rules/*.md` — Cursor rules (свой формат с frontmatter).
- `_tmp/**/*.md` — рабочая зона, к документации проекта не относится.
- `node_modules/**`, `.git/**` — внешние артефакты.
- `CHANGELOG.md` (если появится) — стандарт «Keep a Changelog».
- `LICENSE*`, `AGENTS.md`, `CONTRIBUTING.md`, `*/SKILL.md` — каждый со своим стандартом.

## Создание новых документов требует одобрения

Согласно `general.md`, AI не создаёт новые документы без явного одобрения пользователя. Эти правила применяются **после** одобрения. Обновление существующих документов в рамках текущей задачи — без отдельного одобрения (см. `multi-stage-workflow.md`, п. 4).

## Базовые правила

### Язык и оформление
- Язык документации — русский. Технические термины (endpoint, middleware, JWT, refresh-токен и т.п.) — без перевода.
- Без эмодзи в заголовках и абзацах текста. Исключение: маркеры в таблицах сравнения (✓/✗/⚠) допустимы.
- Корневой `README.md` — витрина проекта для GitHub. В нём допустимы эмодзи в заголовках и развёрнутое вступление. Все остальные правила (запрет на «Последнее обновление», запрет на оглавление, формат API-эндпоинтов, cross-references) — применяются и к нему.
- Без блоков «Последнее обновление: ...» / «История изменений» — это есть в git.
- Без оглавления в начале файла — markdown-рендеры строят его автоматически.

### Содержание
- Один факт — одно место. Если факт уже описан в другом документе, ставь ссылку, не копируй.
- Не дублируй то, что есть в коде. Документируется только то, что не очевидно: контракты API, инварианты, design decisions, edge cases.
- Дерево проекта только в двух местах: backend — в `backend/docs/architecture.md`, frontend — в `frontend/README.md`. В остальных доках — ссылка. Не описывать отдельной строкой каждый тривиальный файл (типа `// Точка входа` к `app.js`) — комментарий рядом с файлом нужен, только если роль файла неочевидна из имени.
- Без вводных абзацев типа «Базовый URL: ...» как отдельного раздела. Такая информация — одной строкой в самом начале файла.

## Заголовки

- `#` — заголовок документа, один на файл.
- `##` — основные разделы.
- `###` — подразделы.
- `####` — отдельные эндпоинты / функции / поля. Глубже не уходить.
- Без знаков препинания в конце заголовка.

## Формат API-эндпоинтов

Структура файла API-документа в целом:

```markdown
# API: <имя сущности>

Базовый URL: `/api/<resource>`. Все запросы требуют `Authorization: Bearer <accessToken>`. <Дополнительные общие требования, если есть — одной строкой.>

## <Контракты данных> (если несколько эндпоинтов возвращают один тип)

`<TypeName>`:
- field: type (constraints)
- ...

## <Группа эндпоинтов>

#### METHOD /path → CODE
...
```

Шаблон одного эндпоинта:

```markdown
#### METHOD /path → CODE

Одна строка о назначении (опционально, только если не очевидно из пути).

**Auth:** выбери одно из: Bearer | Bearer + CSRF | Bearer + admin | none
**Body:** `{ field: type (constraints), ... }`
**Response:** `{ field: type, ... }` или `204 No Content`
**Sets cookies:** `cookie_name` (флаги, path, ttl), ... — одной строкой через запятую. Опускать секцию, если ничего не выставляется.
**Errors:** `400 текст` · `404 текст` · `500 текст`
**Rate limit:** имя лимитера (например, `authLimiter`, по умолчанию 10/15 мин). Опционально — указывать только для эндпоинтов под rate-limit.
**Notes:** одна-две строки про неочевидное поведение (опционально)
```

Правила:
- Тело и ответ описывай TypeScript-подобной inline-сигнатурой, а не полноразмерным JSON.
- Полный JSON-пример — максимум один на эндпоинт, только если структура нетривиальна.
- Не повторяй блок «требует Authorization» в каждом эндпоинте — выноси в одну строку в начало файла.
- Если несколько эндпоинтов возвращают один и тот же тип (`Bookmark`, `User` и т.п.) — опиши тип один раз в разделе сущности и ссылайся на него.

## Формат документа об утилите / модуле / хуке

Шаблон:

```markdown
# <Название модуля>

Назначение в одну-две строки.

## API

#### functionName(args) → ReturnType
Что делает в одну строку. Edge cases / инварианты — следующей строкой, только если есть.

## Алгоритм (если документ об алгоритме)

Описание ключевых шагов и решений — списком или короткой ASCII-схемой. Без пересказа кода.

## Конфигурация (если есть)

- `ENV_VAR` — назначение, default

## Инварианты (если есть)

- ...
```

Правила:
- Раздел `## Алгоритм` нужен только если поведение модуля нетривиально и не выводится из сигнатуры (например, классификация и группировка событий, обработка edge cases по календарю). Для обычных утилит — пропустить.
- Не описывай каждый параметр функции отдельным абзацем, если сигнатура говорит сама за себя.
- Если сигнатура самодостаточна — допустим заголовок `#### functionName(args) → ReturnType` без текста под ним. Текст добавляй только когда есть нетривиальное поведение / инвариант / edge case.
- Примеры сценариев — максимум 1–2 ключевых на документ, остальное выводится из тестов.
- Связанные файлы / используемые утилиты — не перечислять (это видно из импортов).

## Описания полей

- Предпочтение — inline-сигнатура (`{ email: string, password: string (min 6) }`).
- Список «поле — описание» нужен только когда у поля нетривиальные constraints / поведение, не помещающиеся в сигнатуру.
- Сокращения для constraints в сигнатурах: `string (min 6)`, `int (≥0)`, `'user' | 'admin'`, `optional`, `nullable`. Не писать «string, required, valid email format» — этого избегать.

## Code blocks

- Только когда показывают реальный синтаксис (SQL, bash, TypeScript-сигнатура, fetch-пример, JSON-схема).
- Не оформляй как code block то, что является обычным текстом или списком.
- Длинные SQL/код-блоки сокращай комментарием-заглушкой (`-- ...`, `// ...`), если детали не важны для контракта.

## Списки vs проза

- Факты, поля, ошибки, инварианты — списком.
- Проза допустима только для коротких объяснений «почему так» (1–3 предложения).
- Список из 7+ пунктов без подзаголовков — сигнал, что нужны подразделы.

## Cross-references

- Относительные markdown-ссылки на другие документы: `[POST /api/auth/refresh](./api-auth.md)`.
- Якоря на конкретный заголовок (`#post-apiauthrefresh-200`) — хрупкие (зависят от рендера и точного текста заголовка). По умолчанию ссылайся на файл целиком; якорь добавляй только если проверил, что он работает в твоей среде рендера.
- Не дублируй содержимое связанного документа.

## Целевые размеры

- README директории — до 100 строк.
- README с обязательным деревом проекта или разделом AI Task Context (`backend/docs/architecture.md`, `frontend/README.md`) — до 150 строк.
- API-документ одной сущности — до 200 строк.
- API-документ нескольких тесно связанных сущностей одного роута (например, Bookmark + Category + Tag в `/api/bookmarks/*`) — до 300 строк.
- Архитектурный документ — до 150 строк.
- Документ об утилите/хуке — до 150 строк.
- Справочник схемы БД (таблицы, поля, индексы) — до 220 строк.

Превышение — сигнал, что есть дублирование или документ нужно разбить.

## При обновлении существующего файла

- Не возвращай удалённые эмодзи / «Последнее обновление» / оглавление, даже если они были в старом стиле.
- Не разворачивай inline-сигнатуры обратно в полные JSON-примеры.
- Если новая фича добавляет API-эндпоинт — описывай его строго по шаблону выше.
- Если новая фича повторяет уже описанное в другом файле — добавь ссылку, а не дубль.

## При создании нового файла (после одобрения пользователя)

- Используй шаблоны из этого rule.
- Перед созданием убедись, что для этой темы ещё нет существующего документа — расширяй его, а не плоди новый.

## Что не должно попадать в документацию

- TODO-листы и планы — в `_tmp/` или issue-трекере.
- Точные версии зависимостей — есть в `package.json` (см. правило «не дублируй то, что есть в коде»).
- Очевидные пояснения («главный файл приложения», «утилита для работы с датами»).
- Прозаические переходы и пересказ собственного содержания.
