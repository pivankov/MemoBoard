# Правила работы по поэтапной инструкции

> Применяй эти правила всегда, когда работаешь по заранее подготовленной поэтапной инструкции (например, файл `_tmp/tasks/<task-slug>/`). Цель — стабильное качество и минимум перерасхода токенов между этапами.

---

## 1. Запрет на длительные процессы

Не запускай dev-серверы, watcher-ы и любые длительные процессы (`npm start`, `npm run dev`, `node server.js`, `nodemon`, `vite`, и т.п.) для самопроверки.

- Если для проверки этапа реально нужен запущенный backend/frontend — **попроси пользователя подтвердить, что нужный сервис уже поднят**, и продолжай.
- Если процесс всё-таки пришлось запустить — **обязательно останови его до завершения этапа** (`kill <pid>`, `pkill -f <pattern>`). В отчёте об этапе явно укажи: «процессов после этапа не оставлено».
- Перед запуском чего-либо длительного **сначала проверь, не запущен ли уже такой процесс** (терминалы / `ps`). Если запущен — не дублируй.

Допустимо без ограничений: разовые быстрые команды (`npm run build`, `tsc --noEmit`, `npm run lint`, `npm test -- --watch=false`, `curl`, `sqlite3 … "SELECT …"`).

## 2. Делай ровно один этап

Если пользователь явно указал номер этапа (например, «реализуй этап 3»), делай только этот этап. Не «забегай вперёд», даже если соседний этап тривиальный.

Исключение — если в инструкции явно сказано, что этапы объединены, или пользователь попросил несколько этапов сразу.

## 3. Не разведывай то, что уже описано

В качественной инструкции уже перечислены все затрагиваемые файлы и сниппеты. Не запускай `Grep`/`Glob`/семантический поиск для повторного открытия того, что и так указано.

Разведывать стоит только если:
- инструкция ссылается на сущность без пути и её действительно нужно найти;
- ты столкнулся с противоречием между инструкцией и реальным состоянием кода (тогда сначала зафиксируй противоречие в отчёте).

## 4. Документацию обновляй внутри того же этапа

Если в этапе появилась новая фича/API/тип/роут — актуализируй соответствующую документацию (`backend/docs/*`, `frontend/docs/*`, `README.md`, `backend/db/README.md`) **в этом же этапе**, не откладывая на «финальную полировку».

Отдельный этап «полировка документации» не нужен, кроме случаев, когда инструкция явно его требует.

## 5. Самопроверка — дёшево и по делу

Для подтверждения этапа предпочитай самые дешёвые проверки:

1. Статика: `tsc --noEmit`, `npm run build`, lint, `ReadLints`.
2. Точечный SQL: `sqlite3 backend/db/data.db "…"`.
3. Точечный `curl` (только если backend уже поднят пользователем).
4. Чтение собственного диффа — мгновенно и бесплатно для качества.

Не имитируй e2e-сценарии в браузере и не «прокликивай» UI. Если этап требует ручной проверки в UI — попроси пользователя проверить по чек-листу.

## 6. Формат отчёта об этапе

После завершения этапа выдай короткий отчёт строго по структуре:

1. **Что сделано** — 3-7 пунктов.
2. **Изменённые / созданные файлы** — список с путями.
3. **Проверки** — какие команды запускал и что они показали.
4. **Процессы** — «не запускал» либо «запускал X, остановил».
5. **Замечания** — что отклонилось от инструкции, что обнаружено по пути, что предлагаешь дальше. Если отклонений нет — одна строка «нет».

Без воды, без повторения инструкции, без эмодзи.

## 7. Если инструкция противоречит коду

Если ты обнаружил, что инструкция расходится с реальным состоянием проекта (файл переехал, API изменился, появилась новая зависимость) — **остановись и зафиксируй расхождение в отчёте**. Не импровизируй молча. Пользователь решит: править инструкцию или править код.
